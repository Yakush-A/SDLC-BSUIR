# Загружать портрет через проверяющий клиент с защитой от SSRF

## Контекст и постановка задачи

Адрес портрета (`portraitUrl`) вводит пользователь, а загрузку по нему выполнит сервер. Без защиты это позволяет заставить сервер обращаться к внутренним адресам (SSRF) или исчерпать память большим изображением (REQ-SEC-002, REQ-SEC-003). При любом сбое экспорт должен продолжиться с заглушкой (REQ-REL-001).

Вопрос: как безопасно получать портрет на стороне сервера?

## Драйверы решения

* Запрет обращения к loopback, частным, link-local адресам и метаданным облака (REQ-SEC-002)
* Таймаут 5 с, размер до 5 МБ, не более 3 перенаправлений (REQ-SEC-003)
* Защита от подмены DNS между проверкой и подключением (DNS rebinding)
* Устойчивость: сбой не прерывает экспорт (REQ-REL-001)
* Размер PDF: портрет не должен раздувать файл (REQ-PERF-003)

## Рассмотренные варианты

* Собственный клиент с проверкой адресов в DNS-резолвере
* Белый список доменов
* Браузер загружает изображение и передаёт байты в запросе
* Не выводить портрет

## Итог решения

Выбранный вариант: «Собственный клиент с проверкой адресов в DNS-резолвере», потому что проверка выполняется там же, где определяется адрес подключения, поэтому закрывает подмену DNS, и не требует поддержки списка доменов.

Правила `UrlGuard`: схемы `http` и `https`; порты 80 и 443; все полученные адреса проверяются (запрещены loopback, any-local, site-local, link-local, multicast, `169.254.0.0/16`, `fc00::/7`); перенаправления выполняются вручную с повторной проверкой каждого шага, максимум 3; таймаут 5 с; чтение прерывается на 5 МБ; тип определяется по сигнатуре файла (PNG, JPEG), а не по заголовку; размер в пикселях не более 25 млн, затем изображение уменьшается до 1500 пикселей по большей стороне. Любая ошибка даёт `Placeholder`. Для тестов есть свойство `sheetexport.image.allow-private`, по умолчанию выключено.

### Последствия

* Хорошо, потому что сервер нельзя использовать как прокси во внутреннюю сеть.
* Хорошо, потому что сбой портрета никогда не приводит к ошибке экспорта.
* Хорошо, потому что уменьшение изображения удерживает размер PDF (REQ-PERF-003).
* Плохо, потому что нужен собственный код и зависимость `httpclient5` (версия управляется BOM Spring Boot, лицензия Apache-2.0) ради подключаемого резолвера.
* Плохо, потому что часть легитимных хостов (интранет, локальные адреса) работать не будет, это допустимо для публичного сервиса.

### Подтверждение

* Тесты `PortraitSecurityTest`: ссылки на `127.0.0.1`, `10.0.0.5`, `169.254.169.254`, `file:///etc/passwd`, перенаправление на внутренний адрес, медленный хост, файл 10 МБ, цепочка из 5 перенаправлений дают заглушку (REQ-SEC-002, REQ-SEC-003, REQ-REL-001).
* Тест `ImageScalingTest`: изображения 1×1, 100×1000, 1000×100, 5000×5000 вписываются в рамку без искажения (REQ-FUNC-020).

## Плюсы и минусы вариантов

### Собственный клиент с проверкой в DNS-резолвере

* Хорошо, потому что закрывает DNS rebinding.
* Хорошо, потому что не требует списка доменов.
* Плохо, потому что больше собственного кода (WP-09, 10 ч).

### Белый список доменов

* Хорошо, потому что очень простая и надёжная защита.
* Плохо, потому что пользователи указывают произвольные хосты, список был бы слишком узким.

### Браузер загружает изображение

* Хорошо, потому что сервер не обращается во внешний мир.
* Плохо, потому что внешние хосты часто запрещают чтение из браузера (CORS), и формат запроса экспорта усложняется.

### Не выводить портрет

* Хорошо, потому что нет рисков.
* Плохо, потому что нарушает REQ-FUNC-020 и ожидания пользователей.

## Дополнительная информация

* Связано: SRS REQ-INT-010, REQ-SEC-002, REQ-SEC-003, REQ-REL-001, REQ-FUNC-020; SDD DV-ALG-03.
* Пересмотреть, если проект получит собственное хранилище загруженных изображений.
