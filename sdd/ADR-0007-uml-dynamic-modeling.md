# Моделировать динамическое поведение на UML средствами PlantUML

## Контекст и постановка задачи

Для модуля Sheet Export нужна модель динамического поведения: варианты использования, поток экспорта, жизненный цикл кнопки и задания Renderer, взаимодействие frontend, backend и Typst Renderer. Модель должна быть связана с SRS и SDD, храниться в репозитории рядом с документацией и изменяться вместе с ней.

В SRS уже используются модели SysML v2 для контекста, вариантов использования и архитектуры. Для ЛР5 требуется именно UML-модель динамического поведения с диаграммами вариантов использования, активности, состояний и последовательности, а также с описаниями актёров и прецедентов.

Вопрос: чем и как описывать UML-диаграммы, как обеспечить их версионируемость, единое оформление и прослеживаемость к требованиям?

## Драйверы решения

* Поддержка четырёх типов UML: вариантов использования, активности, состояний и последовательности
* Текстовое представление, пригодное для git, code review и просмотра diff
* Стандартная нотация UML 2.x, близкая к примерам из задания на ЛР5
* Отсутствие платных инструментов и обязательных внешних сервисов
* Прослеживаемость: прецедент → активность → состояние → последовательность → требование SRS
* Согласованность с уже существующими документами `srs/`, `sdd/` и ADR-0001 … ADR-0006
* Монохромное оформление без цветных заливок, теней и «человечков» для внешних систем

## Рассмотренные варианты

* PlantUML (диаграммы как текст)
* Mermaid (диаграммы как текст, встроенная поддержка GitHub)
* Графический редактор draw.io / Visio
* Только SysML v2, уже используемый в SRS

## Итог решения

Выбранный вариант: «PlantUML», потому что он покрывает все четыре требуемых типа UML в стандартной нотации, остаётся текстом и позволяет хранить диаграммы в git вместе с документацией.

Структура хранения:

```text
uml/
├── README.md
├── glossary.md
├── supplementary-spec.md
├── use-cases.md
└── diagrams/
    ├── uc-01-use-case.puml | .png
    ├── ad-01-export-pdf.puml | .png
    ├── sm-01-export-button.puml | .png
    ├── sm-02-render-job.puml | .png
    ├── sd-01-export-pdf.puml | .png
    └── sd-02-handle-errors.puml | .png
```

### Механизм построения и связи диаграмм

Диаграммы строятся последовательно, каждая следующая уточняет предыдущую:

1. **Варианты использования** выводятся из требований SRS. Актёры — внешние лица и системы; каждый прецедент связан с требованиями и имеет описание в `uml/use-cases.md`.
2. **Активность** детализирует основной поток `UC-01`: выбор файла, сохранение правок, запрос, проверки backend, вызов Renderer, запись PDF и обработку ошибок.
3. **Состояния** описывают жизненный цикл двух ключевых сущностей: кнопки `ExportPdfButton` (`SM-01`) и задания рендеринга в Typst Renderer (`SM-02`).
4. **Последовательности** связывают сценарий с компонентами SDD: успешный экспорт (`SD-01`) и обработка ошибок (`SD-02`), включая создание и уничтожение рабочего каталога.

| Прецедент | Активность | Состояния | Последовательность | Требования SRS |
|-----------|------------|-----------|--------------------|----------------|
| UC-01 Экспортировать лист персонажа в PDF | AD-01 | SM-01, SM-02 | SD-01, SD-02 | REQ-FUNC-001 … 008, 021; REQ-INT-004, 009; REQ-SEC-001 |
| UC-02 Выбрать место сохранения | AD-01 | SM-01 | SD-01 | REQ-FUNC-003, 004, 006, 007 |
| UC-03 Сохранить отложенные правки | AD-01 | SM-01 | SD-01 | REQ-FUNC-008 |
| UC-04 Сформировать PDF | AD-01 | SM-02 | SD-01, SD-02 | REQ-FUNC-009 … 020, 022, 023; REQ-INT-011; REQ-REL-002, 003 |
| UC-05 Подготовить портрет | AD-01 | SM-02 | SD-01 | REQ-INT-010; REQ-SEC-002, 003; REQ-REL-001; REQ-FUNC-020 |
| UC-06 Сохранить PDF стандартным скачиванием | AD-01 | SM-01 | SD-01 | REQ-FUNC-007 |
| UC-07 Показать ошибку экспорта | AD-01 | SM-01 | SD-02 | REQ-FUNC-021; REQ-REL-003 |
| UC-08 Подключить игровую систему | — | — | — | REQ-REUSE-001 … 004; REQ-MAINT-002 |

Для `UC-08 … UC-10` отдельные диаграммы активности, состояний и последовательности не строятся: эти прецеденты не участвуют в основном сценарии экспорта, а их поведение полностью описывается текстом и требованиями. Это осознанное ограничение модели, а не пропуск.

### Оформление

* Монохромный стиль: белый фон, чёрные линии и текст, без теней и цветных заливок.
* Люди — `actor` («человечки»); внешние системы — прямоугольники со стереотипом `<<system>>`.
* Use case — `skinparam linetype ortho`; state — `skinparam linetype polyline` (ортогональные сегменты со скруглениями); activity и sequence ортогональны по нотации.
* Шрифт DejaVu Sans; размеры и отступы задаются в `.puml`, а не в графическом редакторе.

### Последствия

* Хорошо, потому что диаграммы версионируются и сравниваются как текст.
* Хорошо, потому что нотация близка к стандартной UML и совпадает с заданием ЛР5.
* Хорошо, потому что цепочка «прецедент → активность → состояния → последовательность → требование» делает модель проверяемой на согласованность.
* Хорошо, потому что PlantUML не требует платных инструментов; PNG можно перерисовать локально.
* Плохо, потому что для получения PNG нужен PlantUML (Java) или внешний сервис; GitHub не рисует `.puml` без экспорта.
* Плохо, потому что PNG нужно перерисовывать при каждой правке исходника.
* Нейтрально: в документации сосуществуют SysML v2 (SRS) и PlantUML (UML-модель ЛР5); это разные языки для разных задач.

### Подтверждение

* Каждый `.puml` рендерится без ошибок PlantUML 1.2025.4; для каждого есть актуальный PNG в `uml/diagrams`.
* Проверка оформления: белый фон, чёрные линии, отсутствие цветных заливок; человечки только у людей; внешние системы — `<<system>>`.
* Проверка идентификаторов: `UC-01 … UC-10`, `AD-01`, `SM-01`, `SM-02`, `SD-01`, `SD-02` совпадают в диаграммах, `use-cases.md`, SDD и ADR.
* Проверка трассируемости: таблица выше и таблица в `use-cases.md` ссылаются на `REQ-…` из SRS.
* Проверка на code review: изменения `.puml` сопровождаются обновлением PNG и описаний.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что поддерживает все четыре требуемых типа UML.
* Хорошо, потому что текстовый формат подходит для git и diff.
* Хорошо, потому что есть локальный CLI и возможность экспорта PNG/SVG.
* Нейтрально, потому что требует Java и отдельного шага рендеринга.
* Плохо, потому что GitHub не отображает `.puml` без экспорта.

### Mermaid

* Хорошо, потому что GitHub рисует диаграммы без дополнительных шагов.
* Плохо, потому что нет полноценной диаграммы вариантов использования.
* Плохо, потому что диаграмма активности выражается блок-схемой, а не нотацией UML.
* Плохо, потому что ограничена поддержка `ref`, создания и уничтожения участников в диаграмме последовательности.

### Графический редактор draw.io / Visio

* Хорошо, потому что полная свобода рисования и ручной компоновки.
* Плохо, потому что объёмные XML-файлы плохо сравниваются в git.
* Плохо, потому что правки вручную трудно согласовывать с требованиями и идентификаторами.
* Плохо, потому что оформление зависит от редактора и легко расходится между диаграммами.

### Только SysML v2

* Хорошо, потому что уже используется в SRS и не вводит второй язык.
* Плохо, потому что в задании ЛР5 требуется UML-нотация динамического поведения.
* Плохо, потому что для диаграмм последовательности и состояний в текущем виде не хватает привычных UML-обозначений.
