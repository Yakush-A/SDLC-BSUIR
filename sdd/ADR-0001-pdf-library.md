# Использовать Apache PDFBox и собственный движок раскладки для создания PDF

## Контекст и постановка задачи

Модулю нужна библиотека, которая создаёт PDF с кириллицей, переносом текста, пагинацией и масштабированием изображений (REQ-FUNC-015 … REQ-FUNC-020). Модуль должен быть изолирован от проекта (REQ-REUSE-001), лицензия библиотеки должна быть совместима с UNLICENSE проекта (REQ-COMP-002), а backend запускается в `eclipse-temurin:21-jre-alpine` без GUI и системных шрифтов.

Вопрос: какая библиотека и какой подход к раскладке дадут проверяемое качество форматирования за отведённое время (бюджет раскладки около 22 ч, см. план)?

## Драйверы решения

* Корректный перенос текста и пагинация при любых данных (REQ-FUNC-016, REQ-FUNC-017, REQ-REL-002)
* Проверяемость результата автотестами: геометрия блоков и извлечение текста (REQ-FUNC-014, REQ-FUNC-018)
* Лицензия: без AGPL/GPL (REQ-COMP-002, CON-4)
* Изоляция: библиотека не должна «протекать» в нейтральную модель листа (REQ-REUSE-002)
* Срок и стоимость: бюджет раскладки и рендера не более 28 ч; компетенции команды — Java
* Работа в headless-окружении Alpine (REQ-PORT-001)

## Рассмотренные варианты

* PDFBox + собственный LayoutEngine
* OpenPDF (высокоуровневые `ColumnText`, `PdfPTable`)
* OpenHTMLtoPDF (HTML/CSS → PDF)

## Итог решения

Выбранный вариант: «PDFBox + собственный LayoutEngine», потому что он единственный сохраняет раскладку (перенос, рамки, продолжение блоков) в нашем коде, независимом от библиотеки, поэтому геометрию можно проверять тестами без парсинга PDF, а саму библиотеку можно заменить, переписав только пакет `render`. Лицензия Apache-2.0 не накладывает ограничений на проект под UNLICENSE.

### Последствия

* Хорошо, потому что раскладка тестируется отдельно: «блок не выходит за рамку» проверяется по координатам, а текст и число страниц проверяются через `PDFTextStripper`.
* Хорошо, потому что только пакет `render` зависит от PDFBox (проверяется ArchUnit), замена библиотеки локализована.
* Плохо, потому что перенос слов, разрыв длинных слов, пагинация таблиц и повтор заголовков нужно написать самим (WP-04a, WP-04b, 22 ч), а в OpenPDF это частично готово.
* Плохо, потому что оценка опирается на документацию и опыт, а не на измерения; риск снимается прототипом WP-01.
* Нейтрально: декодирование изображений использует `javax.imageio`, поэтому в контейнере включается `java.awt.headless=true`.

### Подтверждение

* Прототип WP-01 в итерации 1 должен выполнить критерии REQ-FUNC-016, 017, 018, 020 на тестовых данных в контейнере Alpine.
* Тест ArchUnit запрещает импорт `org.apache.pdfbox.*` вне пакета `dev.ushki.sheetexport.render`.
* Проверка лицензий зависимостей фиксируется в `docs/licenses.md` (REQ-COMP-002).

## Плюсы и минусы вариантов

### PDFBox + собственный LayoutEngine

Apache PDFBox 3.x: низкоуровневый API (страницы, потоки содержимого, шрифты, изображения).

* Хорошо, потому что лицензия Apache-2.0 без ограничений (драйвер «лицензия»).
* Хорошо, потому что раскладка независима от библиотеки и тестируема (драйверы «проверяемость», «изоляция»).
* Хорошо, потому что `PDFTextStripper` годится для приёмочных тестов кириллицы и полноты текста.
* Нейтрально, потому что встраивание шрифтов с подмножеством (subset) поддерживается штатно.
* Плохо, потому что трудоёмкость раскладки выше (драйвер «срок»).

### OpenPDF

Форк iText 4: готовые `ColumnText` (текст в рамке с признаком переполнения) и `PdfPTable` (повтор заголовка, разрыв строк).

* Хорошо, потому что готовы перенос текста в рамке и таблицы, около 8 ч экономии (драйвер «срок»).
* Нейтрально, потому что лицензия LGPL/MPL допускается REQ-COMP-002, но требует учёта условий при распространении.
* Плохо, потому что объекты библиотеки проникают в код раскладки, и геометрию блоков труднее проверять отдельно (драйверы «проверяемость», «изоляция»).
* Плохо, потому что раскладка привязана к API библиотеки, замена дороже.

### OpenHTMLtoPDF

HTML и CSS превращаются в PDF поверх PDFBox.

* Хорошо, потому что вёрстка описывается шаблонами, а перенос и таблицы делает движок.
* Плохо, потому что фиксированные рамки с переходом остатка текста в другой блок (как в листе D&D) в CSS выражаются плохо (драйвер «раскладка по рамкам»).
* Плохо, потому что добавляется HTML-слой и больше зависимостей, а поведение при экстремальных данных сложнее предсказать (драйвер «надёжность»).

## Дополнительная информация

* Условие пересмотра: если WP-04a и WP-04b превысят 28 ч (130% оценки) или прототип не пройдёт критерии, переходим на OpenPDF; изменения затронут только пакеты `layout` и `render`.
* Связано: SRS REQ-FUNC-015 … 020, REQ-COMP-002, REQ-REUSE-001; SDD DV-LOG-01, DV-ALG-01; ADR-0006 (шрифты).
